# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Kiriha is a Windows desktop file manager (Avalonia UI, .NET 10, native AOT) that intentionally combines two UI vocabularies: **Chrome-inspired vertical tabs / bookmarks / settings**, and **Windows Explorer's** navigation and file behavior (plain-text address bar with status-bar breadcrumbs, command bar, shell context menus, quick access, clipboard/DnD semantics). When implementing a feature, the default is "match what Explorer does" unless the feature is inherently tab/browser-shaped (in which case "match what Chrome does").

`Kiriha.slnx` holds two .NET projects: the app (`src/Kiriha/Kiriha.csproj`) and its xUnit v3 test project (`tests/Kiriha.Tests/Kiriha.Tests.csproj`). There is no CI config — verification is local. The repository also contains the local signed-release pipeline in `scripts/release-local.ps1` and the Cloudflare Worker / landing page in `web/`.

## Build & run

```bash
dotnet build src/Kiriha/Kiriha.csproj      # or: dotnet build Kiriha.slnx
dotnet run --project src/Kiriha/Kiriha.csproj
```

Tests:

```bash
dotnet test tests/Kiriha.Tests/Kiriha.Tests.csproj
dotnet test tests/Kiriha.Tests/Kiriha.Tests.csproj --filter "FullyQualifiedName~LocaleDetectionTests"
```

**`dotnet build Kiriha.slnx` and `dotnet build <csproj>` write to two different output trees.** `Kiriha.slnx` pins `Platform=x64`, which lands in `bin/x64/<Config>/…`; building a csproj directly (and `dotnet test`, which resolves the assembly the same way) uses `bin/<Config>/…`. So `dotnet build Kiriha.slnx -c Release` followed by `dotnet test … --no-build` silently runs a **stale** assembly from the other tree and can report an outdated pass count. Prefer plain `dotnet test` (let it build); if you use `--no-build`, build the test csproj itself first, not the solution.

Native AOT publish:

```bash
dotnet publish src/Kiriha/Kiriha.csproj -c Release
# output: src/Kiriha/bin/Release/win-x64/publish/Kiriha.exe
```

From Git Bash, AOT's link step needs vswhere on PATH or it fails:
```bash
export PATH="$PATH:/c/Program Files (x86)/Microsoft Visual Studio/Installer"
```

When an explicit release is requested, use the `vava` workflow: `vava.config.json` invokes `scripts/release-local.ps1`, which publishes and signs the x64/ARM64 Velopack artifacts, uploads them to Cloudflare R2, verifies delivery, and prunes obsolete packages. The script has external effects and reads the Cloudflare credential from `C:\Users\IMT\dev\Secret\secrets.json`; do not use it as a normal build or verification command. `web/worker.js` serves both the landing page and R2-hosted update files through `kiriha.kagayoi.com`.

**`CHANGELOG.md` is the user-facing release notes and every release adds a section to it.** `vava` only updates a changelog that already exists (it deliberately never creates one), so the file's presence is what keeps release notes happening — don't delete it. Entries are Japanese, written for the person using Kiriha: what changed on screen, not which class changed. Work that is finished but not yet in a release goes under `## 未リリース`, which the next release renames to its version heading. `README.md` is user-facing too (install / features / settings / shortcuts / troubleshooting) — developer-facing facts belong here in `CLAUDE.md` instead.

`TreatWarningsAsErrors` is on (`Directory.Build.props`). `IL3053` is suppressed in the csproj — it's a known false-positive from Velopack's COM interop that ILC misreads as invalid IL; don't "fix" it, it's already handled.

`RestorePackagesWithLockFile` is on, so `src/Kiriha/packages.lock.json` is committed and `dotnet restore` validates against it. Changing a `PackageReference` regenerates the lock file — commit that change together with the csproj edit rather than deleting the lock file.

Verification is: build clean (0 warnings), `dotnet test` green, and — for anything touching XAML or interaction — run the Debug exe and screenshot/exercise the actual UI. The tests deliberately cover only what can be checked without touching real user data or a live UI (pure logic, path/format handling, settings serialization, locale resources); a green build and green tests still do not mean a feature works on screen.

**Tests must never touch the real `%LocalAppData%\Kiriha` or `HKCU\Software\Kiriha`.** `AppStoragePaths.OverrideForTests` redirects both, and `AppStorageScope` (tests/Kiriha.Tests/TestSupport.cs) is the `using`-scoped wrapper that sets and restores them. Because that override is static, every test that touches persistence must join the `AppStorageCollection` xUnit collection so they run serially — parallel runs race on the override and can write to the developer's real settings. `TempDirectory` builds throwaway trees (and strips Hidden/System/ReadOnly on cleanup), and `CultureScope.With` pins a culture on a dedicated thread so it can't leak into other tests through async flow.

`xUnit1051` is suppressed in the test csproj on purpose: the concurrency tests coordinate with `Barrier`/`CountdownEvent`, so honoring a cancellation token would turn a failure into a hang instead of a deterministic assert.

## Architecture

**MVVM, one window, tab-scoped state.** `MainWindowViewModel` owns the vertical tab collection, sidebar, bookmarks bar, and window-level settings. Each open tab is an independent `TabViewModel` with its own path, navigation history (`_back`/`_forward` stacks), sort/view state, search/filter, and selection. Folder-change watching is **not** per-tab: `TabViewModel` holds only an `IDisposable` subscription handle and delegates to `DirectoryObservationService` (Services/DirectoryObservationService.cs), which keys one shared `FileSystemWatcher` per normalized Windows path across all tabs (reference-counted, with a debounce) so opening the same folder in multiple tabs doesn't spawn duplicate watchers. The **Settings tab** (`chrome://settings`-style) is just a `TabViewModel` constructed with `isSettingsTab: true` — `IsSettingsTab`/`IsNormalTab` gate which half of `MainWindow.axaml`'s per-tab `DataTemplate` renders. There is no separate settings window.

**Reordering tabs must go through `MoveTabPreservingSelection`, never a bare `Tabs.Move`.** The vertical tab `ListBox` binds `SelectedItem="{Binding SelectedTab}"`, and Avalonia's two-way selection binding does not reliably survive an `ObservableCollection.Move` — `SelectedTab` can end up `null`. That is not a cosmetic glitch: every `IsVisible="{Binding SelectedTab.…}"` binding in `MainWindow.axaml` resolves to `UnsetValue` and falls back to its default (visible), so the tab list and the gallery Exif panel render on top of each other and the content area goes blank. Pin/unpin (`ReorderPinned`), drag-reorder (`MoveTab`) and bulk reorder (`ReorderTabs`) all route through the one helper; call sites that immediately assign `SelectedTab` afterwards (e.g. `NewTabToRight`) are the only exception.

**The sidebar has three mutually exclusive contents — quick access / tree / bookmarks — selected by `MainWindowViewModel.SidebarMode` (`Models/SidebarMode.cs`), and the bookmarks bar that used to sit under the address bar is gone (2026-08-05).** The three chips above the pane are `ToggleButton.chip`s bound to `IsSidebarQuickAccess` / `IsSidebarTree` / `IsSidebarBookmarks`, one-property-per-mode wrappers whose setters only act on `true` so re-clicking the active chip can't leave the pane blank (radio behaviour, which two bools could not express — "tree and bookmarks at once" would be representable). They are **icon-only on purpose**: three labels do not fit the 230 px default width even in Japanese, and several of the 17 languages are longer, so the name lives in `ToolTip.Tip` + `AutomationProperties.Name`. `AppSettings.SidebarMode` is the enum name; the old bool `AppSettings.SidebarShowTree` is **kept as a read-only migration source** (like `UseMaterialIcons`) because shipped settings.json files still carry it — `SidebarModes.Resolve` is the one place that decides, and `SidebarModeHappyTests` pins its table. The bookmark data itself (`AppSettings.Bookmarks`, `BookmarkNode`) is unchanged, so existing users' bookmarks appear in the new pane with no conversion. Drop-to-register still works because the pane `Border` carries the `bookmarkpane` class that `IsOnBookmarkPane` / `ResolveFileDropVisualControl` match on (renamed from `bookmarkbar`); its default `BorderThickness="0,0,0,3"` is transparent so the drop highlight doesn't shift the tree. Unlike the folder tree, the bookmark `TreeView`'s `SelectionChanged` needs no sync guards — nothing in the app ever sets its selection.

**Bookmark rows show the target's real icon, and the two runtime facts that requires are carried on `BookmarkNode` itself rather than rebuilt into a new collection.** `RefreshBookmarkIconsAsync` mirrors `RefreshSidebarAsync` — it walks the tree for link nodes, resolves `(emoji, IImage?, isDirectory)` for every path **off-thread** (`Directory.Exists` blocks on disconnected network paths, and `ShellThumbnailService.TryGetIcon` is a shell call), guards with a generation counter, and writes back through `BookmarkNode.SetIcon`. That is why `BookmarkNode` is an `ObservableObject` with `[property: JsonIgnore]` on `Icon`/`IconImage`/`OwnsIconImage`/`IsDirectoryTarget`: the sidebar can afford `SidebarItems.Clear()` + rebuild, but doing that to the bookmark tree would collapse every expanded group folder on each refresh. `SetIcon` disposes the previous bitmap when this node owns it, which is what makes switching icon sets (`Windows` → `Material`) not leak — Material/emoji images are shared cache entries and must never be disposed. `FileSystemEntry.ResolveEmojiIcon` is `static` for exactly this reason: the emoji table is the file list's, and bookmarks must not fork a second one. **A bookmark can point at a file, not just a folder**, so `IsDirectoryTarget` (resolved by the same pass, defaulting to `true`) is what routes a click to `NavigateTo` vs `OpenBookmarkFile`, and gates middle-click / 「新しいタブで開く」 which only make sense for folders. Group-folder nodes (`Children is not null`) have no filesystem target and keep the 📁 emoji.

**The sidebar tree's `SelectionChanged` is not the same thing as "the user clicked a folder", and treating it as such duplicated tabs.** The tree lives inside the per-tab `DataTemplate`, so every `SelectedTab` change rebuilds it, and the `SelectedItem` two-way binding then pushes the stored `SidebarTreeSelectedItem` into the fresh `TreeView` — which raises `SelectionChanged` with the *previous* tab's node. `SidebarTree_SelectionChanged` used to navigate on that, so switching or reordering tabs teleported the newly selected tab to the old tab's folder; on a **pinned** tab the "navigate elsewhere = open a new tab" rule then appended a tab at the bottom, once per operation. Reproduced by measurement (stack: `set_SelectedTab` → `ContentPresenter.UpdateChild` → logical-tree attach → binding subscribe → `TreeView.SelectSingleItem`), which is why the handler now ignores notifications from a `TreeView` that is not `IsLoaded` yet, plus anything raised while `MainWindowViewModel.IsSyncingSidebarTree` or matching the one-shot echo token `TryConsumeSyncedTreeNodeEcho`. A real click always arrives after `Loaded`, so the guards cost nothing. `MoveTabPreservingSelection` additionally sets `_isMovingTab` so the transient `SelectedTab` → `null` → restore round trip during `Tabs.Move` raises no side effects at all.

**The sidebar tree mirrors the physical path — `PC` → drives → real folders — and deliberately has no virtual roots.** `FolderTreeNode.NodeKind` is only `Computer` (the single root, `Path` = `FileSystemService.ComputerPath` = `""`, children are drives) and `Folder`; the XP-flavored "デスクトップ > マイ ドキュメント / マイ コンピュータ" arrangement was removed on 2026-08-05 because the tree's hierarchy did not match the address bar. `SyncSidebarTreeToCurrentPathCoreAsync` therefore walks one plain `IsSelfOrAncestorOf` step at a time with no special-casing, and `PC` selects the root itself. Adding a shortcut node (Desktop, Downloads, a cloud root) back into the middle of the tree would re-break that correspondence — the sidebar's quick-access list is where those belong.

**The sidebar tree has VSCode-style header buttons plus a VS-style sync toggle (since 2026-08-04).** The five controls above the tree are: new file / new folder / refresh / collapse all (codicon path data — CC BY 4.0, `Assets/Codicons/NOTICE.md`), and rightmost the 「アクティブ ドキュメントとの同期」 `ToggleButton` (VS Solution Explorer's Sync with Active Document, codicon `go-to-file`). Auto-follow (`SyncSidebarTreeToCurrentPathAsync` on navigation / tab switch) is gated on `MainWindowViewModel.SidebarTreeSyncActive` — persisted in `AppSettings.SidebarTreeSyncActive`, default **on**, and turning the toggle on also syncs immediately. `ToggleButton.treehdr` replaces the whole `Template` (like `.chip`) because Fluent's checked state would otherwise paint the accent over the button; the checked look is instead "subtle background + accent-colored `Path`", which requires the icon `Path` to carry **no local `Fill`** (a local value would beat the `:checked` style). Tree contents never watch the file system — the refresh button's `RefreshSidebarTreeAsync` re-enumerates loaded nodes while carrying expansion and selection across by path. **The "match nodes by path" rule has one exception that will silently break refresh if lost: マイ コンピュータ's `Path` is `FileSystemService.ComputerPath` = `""`,** so `ReloadKeyOf` keys it by `NodeKind.Computer` instead — without that, every refresh collapses the entire drive subtree (observed on a real run). Inline creation inserts a `NewTreeItemNode` (a `FolderTreeNode` subclass with its own `DataTemplate`, placed *before* the base template since resolution is first-match) as the target folder's first child; its `Path` stays `""` on purpose so the existing placeholder guards keep it out of selection-navigation and drag. Commit supports VSCode's `a/b/c.txt` nested form, validates per segment (invalid chars / reserved device names / trailing dot-space / duplicates) with the error shown VSCode-style under the box, Enter commits, Esc cancels, and **losing focus commits valid input and cancels the rest** — all tree mutations run inside the `_sidebarTreeSyncDepth` guard so the resulting `SelectionChanged` storm never navigates a tab.

**Shared state that must stay shared across tabs** lives in a few singleton-ish objects passed into every `TabViewModel`, not duplicated per-tab:
- `ShellOptions` (Services/ShellOptions.cs) — show-hidden / show-extensions / show-checkboxes / icon-set (`FileIconSet`: `Original` emoji, `Material`, `Windows` shell icons), with a `Changed` event every tab subscribes to so each option propagates across all open tabs.
- `ClipboardFileService` — process-wide cut/copy state (`CutStateChanged` event) so every tab's file list can show the Explorer-style "cut item is translucent" effect, not just the tab that did the cutting.
- `AppSettings` (Services/SettingsService.cs) — the JSON-serialized (source-generated, AOT-safe) blob persisted to `%LocalAppData%\Kiriha\settings.json`: pinned tabs, bookmarks tree, window bounds, view-mode default, theme, startup path, etc. `MainWindowViewModel` holds the one `AppSettings` instance and writes through `SettingsService.Save` on every relevant mutation — there's no debounce, so don't be surprised by frequent small writes.

**The UI ships in 17 languages and the mechanism is copied from the sibling project `Komorebi`** (`../Komorebi` — check there first when extending localization). `Assets/Locales/<key>.axaml` is one `ResourceDictionary` of `x:String` entries per language; `App.axaml` holds *all* of them as keyed `ResourceInclude`s, and `LocalizationService.SetLocale` swaps just the active one into `Application.Resources.MergedDictionaries`. That is what makes every `{DynamicResource Text.*}` in XAML re-resolve instantly on a language change, with no restart.

- **`Models/Locale.Supported` is the single list of languages.** Adding one means: the entry there, a new `Assets/Locales/<key>.axaml`, and a matching `ResourceInclude` in `App.axaml`. Missing any of the three fails either the build or `LocaleResourceTests`.
- **Every locale file must carry the identical key set** with identical `{0}`/`{1}` placeholder counts. `LocaleResourceTests` enforces both — a key missing from one language would otherwise render as the raw key string in that language only. The test takes `ja_JP` as the baseline and compares the other 16 against it, so there is no key count to keep in sync anywhere; adding a string means adding it to all 17 files (a scripted insert is the practical way) and nothing else.
- **Strings built in C#** (status bar, error text, dynamically built shell/context menus, Exif labels, tray menu) go through `LocalizationService.Text(key)` / `Text(key, args)`, which resolves against `Application.Resources` at call time and returns the key itself when unresolved. Values that are computed once and cached must be re-resolved: `ContextAction`, `DetailColumnViewModel`, `KirihaUpdateStrings` and the settings tab's title hold the *key* and either compute on read or subscribe to `LocalizationService.Changed`. Log messages are deliberately left as Japanese literals — they are diagnostics, not UI.
- **The default is auto-detection, not Japanese.** `AppSettings.Locale` is `""` on a fresh install, and `LocalizationService.MatchLocale` maps `CultureInfo.CurrentUICulture` onto the supported set (zh Hant/TW/HK/MO → `zh_TW`, `fil`/`tl` → `fil_PH`, region variants collapse to the base language, two-letter keys `sa`/`la` match directly, everything else falls back to `en_US`). Only an explicit pick in the settings dropdown writes a concrete key.
- **Avalonia's own built-in strings are localized by redefining its resource keys in the same locale files.** The `TextBox` right-click flyout (search box, address bar in edit mode, every dialog input) is declared by the Fluent theme, which pulls its headers from `StringTextFlyoutCutText` / `StringTextFlyoutCopyText` / `StringTextFlyoutPasteText` — so the menu came up in English. Defining those three keys in `Assets/Locales/*.axaml` overrides them, because a `DynamicResource` raised inside a `ControlTheme` still resolves through `Application.Resources` (where `LocalizationService` merges the active locale) before reaching `Application.Styles`, verified by reading the live menu through UI Automation. Their values are copied from each file's own `Text.Command.Cut` / `Text.Common.Copy` / `Text.Command.Paste` so the wording matches Kiriha's own menus, and `LocaleResourceTests` pins that all three exist in all 17 files. The same trick is how any other Avalonia string would be localized — the key names are readable as UTF-16 literals inside `Avalonia.Themes.Fluent.dll` (`StringScrollBar*`, `StringDatePicker*`, `StringManagedFileChooser*`, …). Only the text flyout needed it: measured on a real run, Kiriha's scroll bars raise no context menu at all, and the date/time pickers and managed file chooser are never shown (Windows uses the native shell dialogs).
- Because there is no Avalonia `Application` in the test process, `LocalizationService.ResolverOverride` (internal, same spirit as `AppStoragePaths.OverrideForTests`) lets the test assembly's module initializer load `ja_JP.axaml` from disk so tests asserting user-facing Japanese keep working.

**Licensing is a one-time purchase with a signed-key scheme** (Services/LicenseService.cs, no external license library). State machine: `Licensed` / `Trial` (14 days, start date persisted in both `%LocalAppData%\Kiriha\trial.dat` and `HKCU\Software\Kiriha\TrialStart`, earliest wins) / `TrialExpired` / `OnlineCheckRequired` (a valid key whose online revocation check hasn't succeeded for 30 days). Keys are `KIRIHA-<base64url(payload)>.<base64url(sig)>`, ECDSA P-256-signed and verified offline against public keys embedded in `PublicKeysSpki` (an array to allow key rotation — never change the key format itself; the private key lives outside the repo in `dev\Secret\kiriha-license`). Purchase and revocation are served by the Sekisho hub (`sekisho.kagayoi.com`, external dependency); revocation checks fall back to the `kiriha.kagayoi.com/license/check` compat proxy. **There is deliberately no device/seat limit** — one purchase means one key that works on any number of machines, and the only enforcement is per-purchase revocation (a refund invalidates the key on every machine at its next check). The app sends only the purchase ID, no device identifier, so a limit could not be added on the hub alone; don't add one without an explicit decision to change the product. When `TrialExpired`/`OnlineCheckRequired`, `MainWindowViewModel.IsLicenseLocked` becomes true: `MainWindow.axaml` shows a modal lock overlay **and** the main-content Grid is disabled via `IsEnabled="{Binding !IsLicenseLocked}"` — both are required (the overlay only blocks pointer input; control-attached `KeyDown` handlers like `FileList_KeyDown` fire before `Window.OnKeyDown`'s lock guard, so keyboard paths are only blocked by the `IsEnabled` binding). Keep all three in sync when touching lock behavior.

**Activation is email + 6-digit code first, license key second** (added 2026-07-26). The key is shown once on the Stripe success page, so on a second machine the user almost never has it — `LicenseService.RequestRecoveryCodeAsync` posts the address to the hub's `POST /license/kiriha/recover/request`, and `RedeemRecoveryCodeAsync` trades the code at `POST /license/kiriha/recover` for the same signed key, which then goes through the **normal `ActivateKey` signature check** — the hub is not trusted just because it answered. Both the settings card and the lock overlay carry the identical two-step UI plus the collapsed "enter a license key instead" fallback; a user who is locked out and has no key must be able to recover from the overlay, so never add the flow to only one of them. Do **not** "simplify" this to email-only: an email address is not a secret, so accepting it alone would mean anyone who knows the address gets a license. The 30 s resend cooldown, the 5-attempt cap and the code expiry all live on the hub — the app only maps status codes (400/429/401/404) onto `Text.License.Msg.*`. There is still no device limit.

**`LicenseService.Deactivate` clears this machine's activation but deliberately keeps the trial start.** The settings card shows the button only while `Licensed`; it drops `license.json`'s key (carrying `MaxSeenUtc` forward for the clock-rollback guard) and falls back to whatever the trial dates say — so a deactivate on an expired trial lands in `TrialExpired`, not a fresh 14 days. Deleting `trial.dat`/`HKCU` there would both hand out a new trial on every press and make the expired-state UI untestable. Re-activating issues a **different key string for the same purchase**: ECDSA signatures are randomized, so only the `{e,p,d}` payload is stable — never compare keys for equality to decide whether something changed.

`Program` enforces a **single process** with a named mutex. Later launches forward up to 32 startup arguments through a current-user-only named pipe, and `App` dispatches them to `MainWindowViewModel.OpenShellPaths` on the UI thread. When changing startup or activation behavior, preserve the pending-activation handoff used before the UI handler is registered. For manual launch testing, make sure the process under test is the first Kiriha instance; otherwise the new process exits after notifying the existing window.

**Windows Explorer parity is implemented via direct Win32/Shell COM interop**, not by shelling out or reimplementing Explorer's behavior in managed code. Read the existing service before adding a new interop point — the pattern is `internal static partial class` + `[LibraryImport]` (source-generated P/Invoke, AOT-compatible) or source-generated COM (`[GeneratedComInterface]`) rather than classic `[ComImport]`/`DllImport`:
- `ShellContextMenuService` — real `IContextMenu`/`IShellFolder` so right-click gives the actual OS verbs (copy, delete, properties, "Open with", extension-installed entries, etc.), not a reimplementation. Note the deliberate scope decision recorded in comments: Windows 11's redesigned context menu is Explorer-internal with no public API, so this shows the classic/full menu instead — that's expected, not a bug to "fix" toward the new visual style. App-added entries go through the optional `ShellMenuExtraItem` (text + action) that `Show` appends **after** `QueryContextMenu`, behind a separator and with a command id outside the shell's 1–0x7FFF range; that is how "エクスプローラーで開く" is offered for folders (`MainWindow.BuildOpenInExplorerItem`, enabled only when every selected path is a directory). Adding it before `QueryContextMenu` would let a shell extension overwrite the id; its left-hand icon is a shell stock icon (`SIID_*`) drawn into a 32bpp DIB and attached with `MIIM_BITMAP` — the HBITMAP must outlive the menu and be `DeleteObject`-ed after `DestroyMenu`. `RemoveOwnVerbItems` then deletes Kiriha's own "Kiriha で開く" entry from its own menus (matching on the canonical verb `WindowsIntegrationService.ContextMenuVerb`, not the display name, which differs per language); the entry stays in Explorer's menu, which is where it is useful.
- `ClipboardFileService` — writes real `CF_HDROP` + `Preferred DropEffect` clipboard formats so Ctrl+X/C/V round-trips with actual Explorer windows.
- `FileOperationService` — `IFileOperation` (the COM API Explorer itself uses) so delete goes to the Recycle Bin and copy/move/delete/rename get the system progress and confirmation UI instead of raw `File.*` operations. **Each call gets its own COM instance on its own dedicated STA thread, and there is deliberately no serializing gate** — that is what lets the user start a second copy while the first is still running. Don't reintroduce a shared lock (the previous `SHFileOperationW` implementation needed one and rejected concurrent calls with a "busy" result; that outcome no longer exists). STA is required because the progress dialog needs a message pump; an MTA thread silently misbehaves. `PerformOperations` reports user cancellation as HRESULT `0x80270000` **and** via `GetAnyOperationsAborted`, so both are checked — treat cancellation as a non-error so no failure message is shown. Error codes reaching the user go through `ToErrorCode` (unwraps `HRESULT_FROM_WIN32`) then `DescribeError` for the Japanese text.
- `QuickAccessService` — reads the real Quick Access shell folder via COM so the sidebar matches the user's actual pinned folders, not a hardcoded guess. It enumerates on a dedicated **STA** thread: that shell namespace extension needs STA, and calling it from the `Task.Run` thread pool (MTA) fails intermittently — the symptom is the sidebar silently falling back to the six standard folders, seemingly at random. `CoInitializeEx` on an MTA thread was tried and was **not** sufficient; keep the STA thread.
- `ShellNewService` — reads the `HKCR\...\ShellNew` registry entries so "New > ..." matches what Explorer would offer on this machine.
- `WindowsIntegrationService` — owns the user-scoped HKCU startup entry, Explorer "Kiriha で開く" verbs, and default folder/drive open association. If registrations change, keep `Program`'s Velopack uninstall callback in sync so uninstall removes or restores everything Kiriha changed.
- `ImageMetadataService` — reads Exif/file properties through `IPropertyStore` (source-generated COM) and lets propsys format the values; see the gallery section below for the mandatory `GPS_NO_OPLOCK` flag.
- `ShareService` — opens the Windows share sheet via WinRT `DataTransferManager` (`IDataTransferManagerInterop` + CsWinRT projections; needs the `net10.0-windows10.0.26100.0` TFM and the `[GeneratedWinRTExposedExternalType]` assembly attribute for the AOT CCW). Reference this when adding new WinRT interop points.

**The file list's right-click menu has three implementations behind one setting, and only one of them is the Win32 menu above.** `AppSettings.ContextMenuStyle` (`Models/ContextMenuStyle.cs`, default `Modern`) picks: **Modern** — Kiriha draws the menu itself in the Windows 11 shape (icon row + curated items + shell-extension entries + "その他のオプションを確認"); **Shell** — Kiriha draws it, but lists the shell's own items unchanged; **System** — the original `ShellContextMenuService.Show` / `TrackPopupMenuEx` path, untouched. Every entry point funnels through `MainWindow.ShowShellContextMenu`, and the custom path falls back to Win32 whenever `ShellMenuSession.Create` returns null, so a broken shell extension can never leave right-click dead. Things that are load-bearing here:

- **`ShellMenuSession` (Services/ShellMenuSession.cs) harvests, it does not display.** It runs the same `SHBindToParent` → `GetUIObjectOf` → `QueryContextMenu` sequence as the Win32 path but then walks the `HMENU` with `GetMenuItemInfoW` into `ShellMenuItem` records. Its P/Invoke declarations deliberately duplicate a few of `ShellContextMenuService`'s: the proven Win32 display path is what "System" ships, and it was not worth refactoring it to share plumbing.
- **Submenus need `WM_INITMENUPOPUP` before they contain anything.** 「送る」/「新規作成」 and several third-party handlers populate lazily, so `ReadSubMenu` sends the message through `IContextMenu3.HandleMenuMsg2` (or `IContextMenu2.HandleMenuMsg`) before enumerating. Without it those submenus come back empty and get dropped as "empty popup".
- **The COM session must outlive the popup, and the chosen action must run *after* it closes.** `ExplorerContextMenu` stores the click in `_pending` and runs it from `Closed` at `DispatcherPriority.Background`, then disposes the session. Invoking a shell verb while the popup is still up leaves the extension's modal UI underneath it; disposing on `Closed` directly races the click. Verified end to end by automation: clicking プロパティ really does open the shell property sheet for the right file.
- **Which shell items Modern hides is decided by canonical verb, and the exclusion set is filled in as curated items are actually added.** The icon row is `cut`/`copy`/`copyaspath`/`rename`/`Windows.ModernShare`/`delete`/`properties` — パスのコピー sits right of コピー and プロパティ right of 削除 — and `BuildHeaderRow` registers exactly those verbs as excluded, so all seven are hidden only when the row is actually shown. A background right-click has no icon row (`SelectionMatches` is false), and there プロパティ is re-added as an ordinary item targeting the current folder; `pintohomefile` is excluded only when it adds お気に入りに追加 (folders). Matching on display names would need a 17-language table, and a static exclusion list would delete functionality on the paths where Kiriha does not substitute anything. Measured verbs on a real machine: `openas`, `pintohomefile`, `copyaspath`, `Windows.ModernShare`, `PreviousVersions`, `link`; third-party entries report a GUID or nothing, which is exactly why they survive the filter.
- **Modern keeps only directly-invocable, non-Windows shell commands — every shell submenu is dropped.** `IsThirdPartyShellItem` requires a command id, and rejects any verb in `WindowsShellVerbs` unless it is also in `KeptWindowsVerbs` (`openas`, `pintohome`, `pintostartscreen`, `pintohomefile` — the ones Windows 11 itself still shows). Submenus go regardless of owner, because **there is no signal that separates a Windows submenu from a third-party one**: measured on a real machine, the children of 送る (ids 30–31) and of アクセスを許可する (86–87) carry no verb at all, and so do the children of the third-party proCertum SmartSign (82–84) — the id ranges overlap too. Sending them all to 「その他のオプションを確認」 (and to the Shell mode) is what keeps the menu short and predictable; the cost is that a submenu-shaped extension such as 7-Zip is one extra click away in Modern.
- **The menu paints `MenuBg`, never `ContentBg`, and that is not a cosmetic preference.** `ThemeService.ApplyAcrylicBackgrounds` *rewrites* `ContentBg` at runtime to alpha `0xE6` while acrylic is on, which works in the main window only because an `ExperimentalAcrylicBorder` sits behind it. A popup is its own `PopupRoot` with nothing behind it, so the same brush made the file list read straight through the menu (confirmed on a real screen capture — `PrintWindow` composites over black and hides the problem, so verify this with `CopyFromScreen`). `MenuBg` is the menu-specific density (`MenuAlpha` `0xE0`, opaque when acrylic is off), the template puts its own `ExperimentalAcrylicBorder` behind it, and `ExplorerContextMenu.ApplyPopupTransparency` gives the popup window the same `TransparencyLevelHint` the main window uses. The acrylic border's visibility rides on the `MenuAcrylicVisible` resource bool rather than a binding, because submenu popups are not reachable from the view.
- **The menu must not reserve its own margin for a `BoxShadow`, and its rounded corners come from DWM, not from the `Border`.** Acrylic is applied to the popup *window*, so any part of that window the rounded `Border` does not cover — a shadow margin, or just the four corners — renders as a **square** slab of acrylic and reads as "the base is sticking out past the frame" (measured: with a 6 px margin the band around the menu was filled rather than transparent). So the template has no margin and no `BoxShadow`; `ApplyPopupChrome` sets `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND` on the popup HWND and `WindowManagerAddShadowHint` is `True`, which gives OS-clipped corners plus a real system shadow. Verified by sampling a capture: crossing the left edge goes `#171E26` (shadow) → `#3C4045` (the 1 px border) → `#202934` (fill), and the corner is antialiased against the content behind. Submenus live on their own popup windows, so `OnSubmenuOpened` runs the same `ApplyPopupChrome` on each of them — a submenu added without that hook would come back square.
- **`SelectionMatches` decides whether curated items may act on the tab selection.** Right-clicking the background targets the current folder, not the selection, so the icon row and 開く / パスのコピー are omitted there and the shell items carry those functions instead.
- **Japanese/Chinese/Korean shell menus post-fix the access key as `(&H)`.** Stripping only the `&` leaves a visible "(H)"; `StripMnemonic` removes the whole parenthesised group (half- and full-width) first.
- **`MenuItem.HasSubMenu` is not an `AvaloniaProperty`**, so the chevron cannot be `TemplateBinding`-ed. The theme shows it by default and hides it on the `:empty` pseudo-class.
- **The ControlThemes live in `Views/ExplorerMenuStyles.axaml`, merged into `Application.Resources`, and are keyed rather than implicit.** Application scope is required because the popup is a separate `PopupRoot` whose resource chain must still resolve; keying them (`ExplorerMenuItemTheme` etc., assigned in code via `TryFindResource`) is what keeps the existing tab / sidebar / bookmark `MenuFlyout`s on the Fluent look instead of silently restyling the whole app.

**Per-folder view memory (`folder-views.json`) and the configured default are two halves of one rule.** `FolderViewSettingsService` remembers view mode, icon size, sort and — since 2026-07-26 — the detail column widths for each folder; a folder with no record gets the default the user picked in settings (`AppSettings.DefaultViewMode` / `DefaultSortKey` / `DefaultSortAscending`), applied by `ApplySavedFolderViewSettings` on every navigation, not just on new tabs. Those three settings are deliberately **not** updated from the last used view any more — a value the settings screen owns must not rewrite itself when the user changes a folder's view (`DefaultIconSize` still follows the last used size because there is no UI for it). Everything that writes a tab's view state goes through `ApplyFolderViewSettings`, which sets `_isApplyingFolderViewSettings` so applying a default can never create a folder record; `MainWindowViewModel.ResetFolderViewSettings` relies on that when it clears the store and re-applies defaults to the open tabs. In `AddTab` the object initializer runs *after* the constructor, so the saved column widths are re-applied explicitly afterwards — swapping those two lines silently drops remembered widths.

**Each detail column's default width is written out three times and nothing checks that they agree**: the `[ObservableProperty]` field initializer in `TabViewModel`, the property initializer in `AppSettings` (what a fresh install gets), and the literal in `MainWindowViewModel.ResetFolderViewSettings` (what "既定に戻す" restores). Change one and a fresh install disagrees with a reset. Note also that changing any of them does **not** affect folders already recorded in `folder-views.json` — those keep their remembered width until the store is reset, so verifying a default change means resetting first.

**The detail view's column header scrolls horizontally by transform, not by living in the scroll viewer.** The header `ItemsControl` sits in its own `Grid` row so the list can keep its vertical virtualization, so `DetailsList_ScrollChanged` pushes the list's `Offset.X` into `TabViewModel.SetDetailHeaderOffset`. It writes into a `TranslateTransform` the XAML binds whole (`RenderTransform="{Binding DetailHeaderTransform}"`) for the same reason the gallery does: `RenderTransform` lives outside the visual tree and does not inherit `DataContext`. Reaching the header by `x:Name` does **not** work — inside a `DataTemplate` the name is not in a reachable name scope (`FindNameScope()?.Find(...)` returns null, verified with a probe build). The header also needs `ClipToBounds` or the shifted part paints outside the pane.

**The breadcrumbs live in the status bar (moved from the address bar 2026-08-04); the address bar shows the path as plain text.** The address bar's non-edit state is just a `TextBlock` of `PathText`, and clicking it switches to the existing edit `TextBox` — which is why `TabViewModel.CancelPathEditing` (Esc / focus loss) must reset `PathText` back to `CurrentPath`: with breadcrumbs no longer covering the non-edit state, an abandoned half-typed path would otherwise stay visible. The status-bar breadcrumbs keep the full Explorer address-bar behavior (crumb click navigates, chevron dropdown lists subfolders, middle-click opens a background tab), and both flyouts open with `PlacementMode.TopEdgeAlignedLeft` because the bar sits at the bottom edge.

**The breadcrumbs drop the *shallow* end when they don't fit, and that is load-bearing.** `Controls/BreadcrumbPanel.cs` is the `ItemsPanel`: it measures every crumb, packs from the tail backwards, and collapses whatever is left over at the front, so the current folder is always reachable. It replaced a horizontal `ScrollViewer` pinned at offset 0 with `HorizontalScrollBarVisibility="Hidden"`, which pushed the deepest — i.e. most useful — crumbs off the right edge with no visible hint. Three things here are not obvious:

- **Collapsed crumbs are arranged at zero size, and each child needs its own `ClipToBounds`.** `ClipToBounds` on the panel is not enough: a child arranged into an empty `Rect` still renders its content, so without the per-child flag the hidden crumbs paint on top of the visible ones at the left edge (seen on a real capture, not theorized). `IsVisible` is deliberately *not* used — writing it during `MeasureOverride` re-invalidates layout.
- **The overflow count is published as an attached property on the ancestor `ItemsControl`**, because an `ItemsPanelTemplate` has its own name scope and cannot be reached by `#name` from the surrounding XAML. The `…` button is a sibling that binds `IsVisible="{Binding #BreadcrumbItems.(c:BreadcrumbPanel.HasOverflow)}"`.
- **The width feedback loop converges** and does not need damping: showing the `…` button only ever *reduces* the panel's width, and anything that fits in the narrower state also fits in the wider one.

**File list rendering is four parallel `ListBox`es, not one.** `MainWindow.axaml` has separate `ListBox`es for Details / List / Icons / Tiles view, all bound to the same `TabViewModel.Entries`, toggled via `IsVisible` bindings on `IsDetailsView`/`IsListView`/`IsIconsView`/`IsTilesView`.

**「PC」(the drive list) is locked to Tiles.** `TabViewModel.CanChangeViewMode` (`!IsComputerRoot && !IsSettingsTab`) gates `SetViewMode`, the Ctrl+wheel branch and the `IsEnabled` of every view-mode radio item, and `ApplySavedFolderViewSettings` forces `ViewMode.Tiles` for `ComputerPath` **inside the `_isApplyingFolderViewSettings` guard** — without that guard the forced value would be written back as a folder record and, worse, as the tab's remembered state, so returning to a normal folder would arrive in Tiles. `ThemeService` also rewrites **`SettingsPageBg`** with `ContentAlpha`, next to `ContentBg`: it is defined as a static opaque brush in `App.axaml`'s `ThemeDictionaries`, so leaving it alone made the settings tab the one surface that stayed 100 % opaque while acrylic was on (measured: page sampled a flat `#202124` instead of compositing to `#252629` over the island).

**Tiles (「並べて表示」) is pinned to numbers measured off the real Explorer, not chosen by eye.** Ctrl+Shift+7 in Explorer plus `AutomationElement.BoundingRectangle` gives a tile of 313×69 physical px at 125 % scaling — 250×55 dip, pitch 318×74 physical, flowing left-to-right and wrapping down (item 4 of 4 started a new row). So the panel is a plain horizontal `VirtualizingWrapPanel` with `ItemWidth="254" ItemHeight="59"` (the 4 px is the `ListBoxItem` margin), a 48 dip icon, and 16 dip line spacing. Two behaviors are load-bearing and easy to "fix" wrongly: the text column is a **48 dip tall `ClipToBounds` box holding a `MaxHeight="48"` `StackPanel`**, which is what reproduces Explorer's rule that a name wrapping to two lines pushes the size line out of the tile entirely (verified against a capture of both apps side by side) while a folder's single line still centers vertically; and **folders show the name only** — measured on Windows 11, a folder tile has no type and no size line. Tiles do **not** follow the icon-size slider (Explorer's tile size is fixed), so `IconSize` is untouched by `ViewMode.Tiles`. `ViewMode.Tiles` is appended last in the enum because `settings.json` / `folder-views.json` already hold the older members. Thumbnails are gated on `TabViewModel.UsesThumbnails` (`IsIconsView || IsTilesView`) rather than `IsIconsView`, since Explorer shows real thumbnails in tiles; the gallery checks still use `IsIconsView` on purpose. When adding a column or per-row behavior, it typically needs to be wired into all three templates that apply to it (details view has the column grid; icons/list are simpler). List and Icons use `Controls/VirtualizingWrapPanel.cs` to realize only visible/cache rows while preserving `ListBox` selection and DnD; do not replace it with a non-virtualizing wrap panel. `TabViewModel.IconSize` is a free (Finder-style) continuous zoom value — `ViewMode`'s named presets (ExtraLarge/Large/Medium) just set `IconSize` to a fixed number; don't reintroduce a fixed enum-keyed size map.

**Image loading must never run at or above input priority.** Avalonia's dispatcher orders `Background(4) < Input(5) < Loaded(6) < Render(7) < Normal(9)`, so an `await` without `ConfigureAwait(false)` inside a per-row loader resumes at **Normal** — ahead of the user's clicks. With one row per file that is enough continuations to swallow the second half of a double-click on a folder full of images. `EnsureThumbnailAsync` / `EnsureWindowsIconAsync` therefore `ConfigureAwait(false)` every await and hand the finished bitmap back with `Dispatcher.UIThread.Post(..., DispatcherPriority.Background)`; the `EffectiveViewportChanged` / `DataContextChanged` handlers in `MainWindow.axaml.cs` start them with `_ =` instead of `await` so nothing is queued while layout is still running. Measured for reference: the navigation itself (enumerate → sort → filter → breadcrumb → watcher) is 2–5 ms for a local folder; what costs 250 ms+ is Avalonia realizing the rows, so look there before suspecting `NavigateToAsync`.

**Never hand a `FileStream` to Skia or pdfium — decode from memory via `ImageDecodeService`.** `Bitmap.DecodeToWidth(stream, …)` wraps the stream in `SKManagedStream`, so native Skia calls back into managed `Read`. An `IOException` thrown there cannot unwind across the native frames: the caller's `try`/`catch` never runs and the process dies with an unhandled `AppDomain` exception. This is not theoretical — Google Drive's virtual drive (`G:\マイドライブ`) intermittently fails mid-read with `ERROR_INVALID_FUNCTION` / `ERROR_SEM_TIMEOUT` and crashed the app while browsing a photo folder. `ImageDecodeService.TryReadAllBytes` / `TryDecodeToWidth` read the file fully into a `byte[]` first (one retry after 150 ms, since these failures are usually transient), then decode from a `MemoryStream` whose reads cannot fail; both return `null` on failure so preview falls through to info-only display and thumbnails get `MarkThumbnailFinal`. `PdfThumbnailService` does the same for pdfium's stream callbacks. `MaterialIconService` is exempt — it decodes embedded assets via `AssetLoader`, not files.

**Icon-view thumbnails load per navigation generation, in two passes.** `TabViewModel.ThumbnailScope` bundles a linked `CancellationTokenSource`, a 4-slot `SemaphoreSlim`, and the "already loading" set; `ResetThumbnailScope` swaps in a fresh one on every navigation and on entering Icons view, and cancels the old one. Both the token *and* the gate have to be per-generation: cancelling alone is not enough because an in-flight `IShellItemImageFactory.GetImage` on a cloud-synced path (Google Drive) can block for seconds and would keep holding the shared slots, so the folder you just moved to would queue behind the folder you left. Each entry is then loaded twice — `ThumbnailPreviewPixelSize` (96) through the shell first, which returns the file's embedded/thumbcache image almost immediately, then `ThumbnailPixelSize` (320) for the real one — and the gate is **released between the two passes** so every visible row gets its low-res image before any row starts its high-res one. `FileSystemEntry.IsThumbnailFinal` (not `Thumbnail is not null`) is the "done" flag, and it is also set when the high-res pass returns nothing so scrolling doesn't retry forever.

**Re-enumerating the current folder must merge into the existing rows, never rebuild them — rebuilding is what made the file list blink.** `DirectoryObservationService` fires on any change in the folder (600 ms debounce) and `TabViewModel.NavigateToAsync(CurrentPath)` re-enumerates, which used to `DisposeEntryImages(_allEntries)` and hand the `ListBox`es a brand-new `Entries` list: every thumbnail and shell icon in view was thrown away and reloaded even when nothing about those files had changed. Measured with `GetProcessIoCounters` on a folder of 12 images, each watcher tick re-read **2,158 KB** — the whole folder — and a `PrintWindow` capture caught up to 209,250 blank pixels. Three pieces now keep that from happening and all three are load-bearing: `MergeReloadedEntries` reuses the existing `FileSystemEntry` for any path whose `IsSameRowAs` still holds and copies the changed values in with `UpdateFrom` (which is why `Size`/`Modified`/`Created`/`IsHidden`/`IsReadOnly`/`DriveUsedPercent`/`SizeTextOverride`/`DriveFormat` are `[ObservableProperty]` rather than `init` — a row must be able to change without being replaced); `ReplaceEntries` returns early when the new sequence is reference-identical to the current one, so no `ItemsSource` swap happens at all; and `NavigateToAsync` skips `ResetThumbnailScope`, `BuildBreadcrumbs` and the `SelectionText` reset when the path did not change. **Skipping the thumbnail-scope reset is not an optimization** — since the rows are no longer re-created, nothing re-requests their thumbnails, so cancelling the scope would leave anything still loading permanently blank. For the same reason `MergeReloadedEntries` has to call `EnsureThumbnailAsync` itself for a row whose content actually changed (`UpdateFrom` returning true), after `InvalidateThumbnail` — the old bitmap stays on screen until the new one lands, so the row never goes empty. After the change the same measurement reads 0 KB per tick when nothing changed and 28 KB when one image was rewritten, and that image's thumbnail visibly updates.

**Double-clicking an image or a video opens it in gallery full screen, and that is an in-app behavior only — no shell association is registered.** `AppSettings.OpenImagesInGallery` / `OpenVideosInGallery` (both default on) gate it; `MainWindow.TryOpenInGallery` runs before `TabViewModel.Open`, calls `OpenInGallery` (switch to Icons view, push `IconSize` to 160, select the entry) and sets `IsGalleryFullScreen`. Do **not** "complete" this by adding Explorer file associations in `WindowsIntegrationService`: taking over `.jpg`/`.mp4` system-wide is a different product decision, and the point here is that Kiriha handles its own double-clicks. `TabViewModel.IsGalleryImage` is the single definition of "image" for this purpose and includes the camera RAW list, which is also why `UpdatePreview` routes RAW through the shell thumbnail branch — without that the gallery would open on a RAW and show only an icon.

**Gallery mode is a fourth rendering mode layered on top of Icons view, not a separate view mode.** `TabViewModel.IsGalleryView => IsIconsView && IconSize >= 159.5` — it turns on when the size slider is pushed to the top, and `GalleryClose_Click` / Esc leave it by setting `IconSize` back down. Its layout is one `Grid` (`RowDefinitions="*,Auto,Auto"`) holding the large preview `Panel` (`x:Name="GalleryImageArea"`, which also hosts the overlaid `Border.gallerybar`), a `Thumb.rowsplit` divider, and the horizontal filmstrip `ListBox` (`Classes="files gallerystrip"`). Things that are easy to break here:

- **Gallery hides chrome by collapsing rows, not just hiding elements.** The bookmarks bar and command bar each pair `IsVisible="{Binding !IsGalleryView}"` with an `Auto` row definition and an explicit `Height` on the element itself; if you give one of those rows a fixed height again, the chrome will leave an empty band in gallery mode (this is exactly what the status-bar row's old fixed `28` did). The address-bar row stays visible in gallery and collapses only in full screen. The vertical tab strip is also swapped: its tab `ListBox` binds `IsVisible="{Binding !SelectedTab.IsGalleryView}"` while the Exif panel binds the positive, so both live in the same grid row and only one shows.
- **Full screen is window-scoped and view-driven.** `MainWindowViewModel.IsGalleryFullScreen` (not persisted) is the single switch: the address bar, title-bar row, vertical tab strip / Exif panel, `Thumb.rowsplit`, filmstrip and status bar all bind its negation `IsGalleryChromeVisible`, and `MainWindow.ApplyGalleryFullScreen` — reached only through the property's `PropertyChanged` — sets `WindowState` and collapses `RootGrid.RowDefinitions[0]` (the title-bar row keeps its 32 px otherwise). Entering while F11 already put the window in full screen leaves `_galleryOwnsFullScreen` false so leaving doesn't shrink the window. Leaving gallery by any route (Esc, ✕, slider, wheel, tab switch) clears the flag from `Tab_PropertyChanged`/`OnSelectedTabChanged`, so new exit paths need no extra wiring. Esc steps out one level at a time (full screen → gallery), and F11 is redirected to this toggle while in gallery.
- **The filmstrip height is window-scoped, not tab-scoped.** `MainWindowViewModel.GalleryStripHeight` (persisted in `AppSettings`, clamped 54–460) and the derived `GalleryThumbSize` (`GalleryStripHeight - 36`) are reached from inside the per-tab template via `$parent[Window].((vm:MainWindowViewModel)DataContext)`. Keep the drag clamp in `GalleryStripThumb_DragDelta`, the load-time validation, and the derived-size clamp consistent.
- **Wheel behavior is position-dependent** and handled in `OnPointerWheelChanged` before the Ctrl+zoom branch: over the filmstrip, vertical wheel is converted to horizontal scroll; over `GalleryImageArea`, wheel moves the selection via `TabViewModel.MoveGallerySelection`. Both are gated on "not Ctrl" so Ctrl+wheel still zooms out of gallery mode.
- **Background clicks must not clear the selection while in gallery**, because a cleared selection blanks the preview and reads as "the gallery closed". `TryStartMarqueeSelection` returns early for gallery mode, which is the single chokepoint covering all four call sites.
- **All of the gallery's controls live in one bar overlaid on the bottom of the preview** (`Border.gallerybar`, a child of `GalleryImageArea`): rotate left/right, the zoom slider with its percentage readout and a 100% reset button on the left, the video transport (play/pause, seek, mute, volume, loop, rate) in the middle, shown only when `IsVideoPreview`, and full screen + close gallery on the right. There is no separate close button on the image any more — everything is in this one bar. The only other overlay is the pair of large previous/next buttons (`Button.gallerynav`) pinned to the left and right edges of the preview; they call the same `MoveGallerySelection` as the wheel and the ← / → keys, and re-arm the hide timer so they can be clicked repeatedly. The rotate icons are Material Icons `rotate_left`/`rotate_right` path data inlined as `Path.Data` (Apache-2.0, recorded in `Assets/MaterialIcons/NOTICE.md`) — Segoe MDL2 has no matching pair, and hand-drawn arcs looked crude.
- **Rotating a video only turns the picture; it never rewrites the file.** `RotateSelectedAsync` branches on `IsVideoPreview` and steps `GalleryDisplayRotation` by ±90 instead of touching Exif (re-encoding a video would be lossy), so `CanRotateSelected` is true for playable video extensions as well as the Exif-rotatable stills. The rotation resets with `ResetGalleryZoom`, i.e. on every file change and on the 100% button. Because the rotated element is the full-size preview panel, `RotationFitScale` scales 90°/270° back down so the turned frame still fits the area.
- **Zoom is a `RenderTransform`, never a layout change.** `TabViewModel.GalleryZoom` (0.2–8, 1.0 = fit) drives the `ScaleTransform`/`TranslateTransform` pair inside `GalleryImageTransform`, which the XAML binds as one object — `RenderTransform` lives outside the visual tree and does not inherit `DataContext`, so `ScaleX="{Binding …}"` silently does nothing. Keeping it off the layout pass is what lets `Stretch="Uniform"` still compute "fit the area" and leaves the close button and filmstrip in place while zoomed. The zoom slider, the 100% reset button (`ResetGalleryZoomCommand`) and the Ctrl+wheel branch in `OnPointerWheelChanged` (gated on being inside `GalleryImageArea`) all write the same property; zoom/pan reset on every selection change and on entering/leaving gallery. Note this deliberately overrides the old "Ctrl+wheel always leaves gallery" rule **for the preview area only** — over the filmstrip Ctrl+wheel still shrinks `IconSize` and exits.
- **Zoom is anchored to the centre of the preview area by explicit maths, not by `RenderTransformOrigin`.** The transformed `Panel` is pinned to `RenderTransformOrigin="0,0"` and `ApplyGalleryTransform` builds the `TransformGroup` as "move the centre to the origin → rotate → scale → move back (plus the drag offset)", so the middle of the view stays put as the image grows. The area's size reaches the view model through `GalleryImage_SizeChanged` → `SetGalleryViewport`; without that the anchor falls back to (0,0) and the image expands towards the top-left, which is exactly the bug this replaced.
- **The main image area uses a hand (pan) cursor drawn at runtime** (`Controls/HandCursors.cs`) — Windows has no palm-shaped standard cursor and `StandardCursorType.Hand` is the link-pointing finger. The open hand shows on hover and the closed hand while dragging; `UpdateGalleryCursor` is called from the pointer moved/pressed/released handlers.
- **The overlays follow mouse movement, not proximity.** `GalleryImage_PointerMoved` sets `IsGalleryOverlayVisible` and restarts a 2 s `DispatcherTimer` (kept alive while the pointer rests on an overlay, so a slider drag that pauses doesn't make it vanish), `GalleryImage_PointerExited` clears it — but only when the event's `Source` is the area itself, since `PointerExited` bubbles up from the overlays' own controls — and the `.shown` styles fade them in. `GalleryImage_PointerPressed` returns early for presses inside an overlay (`IsGalleryOverlaySource` / `IsGalleryOverlayControl`, which is also what the timer checks); without that, grabbing a slider while zoomed also starts the hand-drag and pans the image.
- **Video volume, mute and playback rate are global and persisted**; loop is deliberately not. The values live in `static` fields on `TabViewModel` so every tab shares them, `MainWindowViewModel` seeds them from `AppSettings` at startup and writes them back through the `TabViewModel.VideoPreferencesChanged` callback (tabs have no `AppSettings` reference). The rate dropdown binds `SelectedIndex` to `VideoRateIndex` — binding `SelectedItem` to a `string` property did **not** write the selection back.

**The gallery prefetches its two neighbours, and the order of operations is the whole point.** `PrefetchGalleryNeighbors` is called *after* the current image has been handed to `PreviewBitmap`, never before — starting the neighbours first makes them compete with the one frame the user is actually waiting for. Decoded neighbours live in `_prefetched` (path → `Bitmap`), and `TakePrefetched` transfers ownership out of the dictionary, so the existing `PreviewBitmap?.Dispose()` on replacement stays correct and nothing is disposed twice. Anything that stops being a neighbour is disposed on the spot; the radius is deliberately 1 because a gallery-width bitmap is ~15 MB. `TakePrefetched` returns null outside gallery view — the preview pane decodes at 480 px, not `GalleryDecodeWidth`. `GalleryDecodeWidth` is 2560 to match a high-DPI panel's physical width (1920 left a 1.33× stretch on every image), and `ImageDecodeService.TryReadPixelWidth` reads the source width straight out of the PNG/JPEG/GIF/BMP/WebP header so a request larger than the original is clamped — decoding *up* would both soften the picture (resampled twice) and blow up memory (a 500 px screenshot held at 2560 px is 26 MB). An unknown format returns 0 and falls back to decoding at the requested width. Measured with a probe build on a 188-file screenshot folder: first move misses, every subsequent move is a cache hit and both neighbours are refilled within ~40 ms.

**Sharpening only works if it is the LAST thing that touches the pixels, so gallery stills are decoded at their on-screen size.** RCAS firms up edges at whatever resolution it runs at; resampling afterwards undoes most of it (a downscale throws the new detail away, an upscale widens it back into a soft edge). So `DecodeGalleryBitmap` runs decode → `CreateScaledBitmap` to the exact **physical** pixel size the image will occupy (fit-to-viewport, never magnified past 1:1, times the window's `RenderScaling`) → RCAS. The on-screen size is then set explicitly: `TabViewModel.PreviewDisplayWidth`/`Height` (physical pixels ÷ `RenderScaling`) with `PreviewStretch = Stretch.Fill`, so the destination rect in device pixels equals the bitmap's pixel count and Skia blits 1:1.

**Never tag those bitmaps with a scaled DPI to express their size.** That was tried and is broken end to end: layout takes the DPI-derived logical size (e.g. 1552×836 for a 1940×1046 bitmap at 120 dpi) but the draw path takes the source rect in *pixels*, so only the top-left 1552×836 pixels get stretched over the whole area — the picture comes out 1.25× too big with its right and bottom cut off. Bitmaps stay at 96 dpi; `GalleryImage` (bitmap + `DisplaySized` flag) is what tells the view how to draw, and the flag rides along in the prefetch cache because it can only be decided when the bitmap is built. Three more things must stay in sync: `SetGalleryViewport` takes the scaling from the view and debounces a 300 ms reload when the area changes, `IsDisplaySizedPreview` gates the whole path (sharpening on, gallery, known viewport, **zoom == 1** — while zoomed the `RenderTransform` magnifies, so a display-sized bitmap would be *worse* than the source-resolution one), and every `PreviewBitmap` assignment goes through `ApplyPreviewDisplaySize` (shell thumbnails pass `null` and stay `Uniform`).

**Gallery sharpening is RCAS (AMD FidelityFX FSR1's second pass). Stills run it on the CPU once per image; video runs it as a Skia runtime shader at draw time.** `ContrastAdaptiveSharpenService` runs the 5-tap cross filter over BGRA pixels, and stills go through it once inside `ImageDecodeService.TryDecodeToWidth(..., sharpen: true)` (gallery call sites only — thumbnails and the 480 px preview pane stay unsharpened). **Video does not touch that code path any more**: paying 7–10 ms of CPU per frame 30 times a second was the whole complaint, so `Services/GalleryShaderService.cs` ports the identical algorithm (RCAS, CAS and the gamma curve) to SkSL and `Controls/VideoFrameView.cs` draws each frame with it through `ISkiaSharpApiLeaseFeature`. `ContrastAdaptiveSharpenService.Enabled` is the one switch, seeded from `AppSettings.SharpenGallery` and flipped by the settings checkbox; `Strength` (Low/Normal/High/Max from `AppSettings.SharpenStrength`) moves the two knobs RCAS actually has — the sharpness constant, and whether the noise-detection term is applied at all (High turns it off, which roughly doubles the effect in textured areas). `FSR_RCAS_LIMIT` is deliberately not one of them: raising it produces ringing, i.e. dirty rather than sharp. **Max is a different filter, not a louder RCAS**: it switches to the original CAS (3×3 neighbourhood, `SharpenCas`/`ProcessRowCas`), whose limiter is looser, so it can go past what RCAS allows at the cost of halos on some material — measured 10.5 ms vs 8.7 ms per 1920x802 frame. Both share the same edge/border handling and the same "flat areas come out bit-identical" property, which is what the tests pin; toggling it calls `TabViewModel.ReloadGalleryPreview` because a decoded still would otherwise keep the old look until the next navigation. Only FSR1's spatial pass is usable here — FSR2/3/4 need motion vectors and depth from a 3D renderer, which a file manager does not have. Two measured traps: `MathF.Max`/`MathF.Min` must stay (rewriting them as `a > b ? a : b` turns them into branches and cost 7 ms → 19 ms per 1920x802 frame on random pixels), and `MathF.Round` per channel was replaced with `+0.5` truncation. Even so a 1920x802 frame costs ~7 ms wall (all cores), which is why video moved to the shader.

**The shader and the CPU filter are two implementations of one algorithm, and `GalleryShaderTests` is what keeps them from drifting.** It runs the SkSL over a raster `SKSurface` and compares every interior pixel against `ContrastAdaptiveSharpenService` / `GammaAdjustService` within 2/255, for all four strengths plus gamma — change one side without the other and it fails. Borders are excluded on purpose: the CPU version copies edge pixels through, the shader replicates them via `SKShaderTileMode.Clamp`. Because both services keep global static state, `GalleryShaderTests` and `ContrastAdaptiveSharpenTests` share the `SharpenSettingsCollection` xUnit collection — running them in parallel makes one read the other's strength setting. Three more things to know: `step` is a reserved SkSL builtin (the uniform is `tapStep`); the tap distance is one *output* pixel but never finer than one source pixel, so zooming in doesn't dilute the effect; and the whole thing degrades to a plain `DrawImage` when `SKRuntimeEffect.CreateShader` fails or no Skia lease is available, with the reason in `GalleryShaderService.LastError`. Measured A/B on a 1920x802 clip: the shader adds ~8 % of one core on top of the drawing cost. Note that a locked console session renders through `D3D10Warp` (software D3D), so any CPU number measured there is a worst case, not what a real GPU session sees.

**Metadata for the gallery panel comes from the Windows property system.** `ImageMetadataService` opens an `IPropertyStore` via `SHGetPropertyStoreFromParsingName` and formats each value with propsys' `PSFormatForDisplay`, so display strings ("f/2.8", "1/125 秒", "4032 x 3024") are produced by Windows and already localized — don't hand-format PROPVARIANTs. The curated `PROPERTYKEY` list is the display order. `TabViewModel.UpdateGalleryMetadata` runs it off-thread with a `CancellationTokenSource` and re-checks `SelectedEntry`/`IsGalleryView` after the await, matching how `UpdatePreview` guards stale results.

**The property store must be opened with `GPS_NO_OPLOCK` (0x80), not `GPS_DEFAULT`.** By default the shell's property handler takes an oplock on the file and the break request can be left unacknowledged. Any later attempt to open that same file **for writing** then blocks forever inside the `FileStream` constructor — no exception, no timeout — which is exactly what gallery rotation does. Symptom when this regresses: the first rotation after app start works, every later one silently does nothing and the rotate buttons stay disabled (the `AsyncRelayCommand`'s task never completes). Verified by measurement: an external process could not open the file for write either until Kiriha was killed. `RotateSelectedAsync` also caps the write with `WaitAsync(RotateTimeout)` so a third-party lock can't permanently disable the buttons.

**Anything that rewrites a whole file in place goes through `AtomicFile` (Services/AtomicFile.cs), not `File.WriteAllBytes`/`WriteAllText`.** Those truncate the target to zero *before* writing, so a crash or an I/O failure mid-write destroys the previous content — for gallery rotation that is the user's photo, and for `license.json` it means the next start fails to parse it, falls back to trial, and a paying user is asked to activate again. `AtomicFile` writes a `.kiriha-<guid>.tmp` **in the same directory** (a temp on another volume would turn the swap into a copy), `Flush(flushToDisk: true)`s it, then `File.Replace` (which carries the original's attributes/ACL/creation time over) with a `File.Move(overwrite: true)` fallback for filesystems that don't implement `ReplaceFile`. Callers today: `LicenseService.Save`, `PngRotationService.TryRotate`, `ExifOrientationService.InsertOrientationApp1`. `ExifOrientationService.WriteOrientationInPlace` is deliberately *not* one — it seeks and writes two bytes, so there is nothing to lose.

**Gallery rotation is lossless by construction, and the format decides how** — `ImageRotationService` is the only entry point the view model calls, and it routes per extension. Both back ends are pure managed, no COM.

- **JPEG / TIFF → Exif only** (`Services/ExifOrientationService.cs`). It never decodes or re-encodes: it rewrites the two bytes of the Exif `Orientation` tag (IFD0 0x0112) in place, so the JPEG entropy data is untouched and the save is instant. A JPEG with no Exif at all gets a minimal 34-byte `APP1` inserted after SOI (still lossless — the compressed data only moves). A file that *has* Exif but no Orientation tag is **not** supported: inserting an IFD entry would mean rewriting every offset in the TIFF block including sub-IFDs, which isn't worth the corruption risk. `ExifOrientationService.CanRotate` therefore covers only `.jpg/.jpeg/.jpe/.jfif/.tif/.tiff`.
- **PNG → pixels are permuted and the file is re-encoded** (`Services/PngRotationService.cs`). PNG has no orientation tag, but its compression is lossless, so inflate → unfilter → permute → re-filter → deflate is still bit-exact; only the byte size moves. Ancillary chunks (`tEXt`, `tRNS`, palette, …) pass through untouched and `pHYs` gets its x/y swapped. **Interlaced (Adam7) PNGs and bit depths below 8 return false** rather than guessing — the first needs seven separate passes, the second packs several pixels into one byte. This is why `RotateTimeout` is 60 s and not the 10 s the Exif path needed: a large PNG really does spend seconds in deflate.

Do not narrow `CanRotate` back to the Exif formats. PNG is the common case for screenshots (the user's own folder is 185 PNG to 3 JPG), and a disabled rotate button with no explanation reads as "rotation is broken". `ExifOrientationTests` pins the 8-value rotation tables and asserts the compressed data is byte-identical after a rotate; `PngRotationTests` asserts that four rotations restore the pixels exactly.

**Because Exif rotation only changes metadata, the decode path has to honor it.** Avalonia/Skia does not apply Exif orientation (verified against the shipped `Avalonia.Skia.dll`), while shell thumbnails do — so before this the two disagreed. `ImageDecodeService.TryDecodeToWidth` now reads the orientation from the same bytes it already loaded and, for values 2–8, rebuilds the bitmap into a `WriteableBitmap` with the pixels permuted. Only 32bpp sources are handled; anything else falls through unrotated rather than guessing.

**Video in gallery mode plays through Media Foundation's Media Engine in frame-server mode** (`Services/MediaEngineInterop.cs`, `Services/VideoPlaybackSession.cs`) — no DXGI device manager, no native HWND. Each frame is blitted into an `IWICBitmap` with `TransferVideoFrame`, copied into a plain BGRA `VideoFrame` buffer (`Services/VideoFrame.cs`, two of them swapped so the binding sees a new instance), and drawn by `Controls/VideoFrameView.cs` — an ordinary control in the visual tree, so every gallery overlay (close button, shell context menu, wheel navigation, marquee suppression) keeps working. The pixels are copied into an immutable `SKImage` on the **UI thread** inside `Render`, and the draw operation owns and disposes it; that is what makes it safe for the render thread to still be drawing frame N while the session is already writing frame N+1. Codec support is whatever Windows has installed. Several things here were learned the hard way and will silently break playback if undone:

- **Never call `IWICBitmap::Lock` to read the frame — use `CopyPixels`.** The `IWICBitmapLock` RCW is a `ComObject`, which does **not** implement `IDisposable`, so `(locked as IDisposable)?.Dispose()` is a silent no-op and the bitmap stays locked. A locked bitmap cannot be written by Media Foundation, so `TransferVideoFrame` keeps returning `S_OK` while the pixels never change — the picture freezes and only advances when the GC happens to finalize a leaked lock. `MediaEngineInterop.ReservedLock` exists only to hold the vtable slot.
- **Release source-generated COM RCWs with `ComRelease.Release`** (`Services/ComRelease.cs`), never `as IDisposable` / `using`. `Marshal.Release` only drops the raw pointer's reference; the RCW holds a separate one. This applies to every COM service in the repo, not just video.
- **`MFStartup` runs once per process and `MFShutdown` is never called** — it is deliberately not even declared. Stopping and restarting the platform between files raced with engine teardown and produced "audio plays, picture is black".
- **One engine per session; switching files calls `Open(path)` (`SetSource`), never a new engine.** `MF_MEDIA_ENGINE_SYNCHRONOUS_CLOSE` is set for the same reason.
- **Frame buffers are rounded to even width/height** (`MakeEven`). YUV 4:2:0 chroma is 2x2, and an odd-sized destination produced frames that arrived but decoded to black (hit with a 1920x802 source scaled to 1280x535).
- **`MaxFrameWidth` is a picture-quality knob, not just a perf knob.** It caps the transfer buffer, so anything above it is thrown away before the frame ever reaches the screen — at the old 1280 a 1080p source was shrunk and then stretched back over a 2560-wide high-DPI gallery, which is what "FHD looks blurry" was. It is now 2560, so 1080p plays 1:1. Measured on a Ryzen 5 7640HS: a 1920x802 30 fps clip renders 910 frames in 31 s (≈29.4 fps, no drops) at ~45 % of one core. Lower it only with a measurement showing the copy is actually the bottleneck.
- **Seek requests are coalesced to one in flight.** The seek slider is a two-way binding, so one drag raises `Seek` dozens of times, and Media Engine's `SetCurrentTime` performs an accurate seek per request without cancelling the one in progress — passing them straight through built a queue and the user waited ~10 s after releasing the thumb. `VideoPlaybackSession.Seek` keeps at most one request in the engine, folds everything that arrives during it into a single pending target, and re-issues on `EventSeeked` (with a 3 s watchdog in case a codec never raises it). `Position` also returns the requested target while a seek is outstanding, because the engine reports the *old* time until the seek lands and the 10 Hz write-back would otherwise drag the slider back under the user's finger.
- **Frames are pulled on the compositor's render frame** via `TopLevel.RequestAnimationFrame` (`TabViewModel.StartVideoPump`), not a `DispatcherTimer`. Win32's dispatcher implements timers with `WM_TIMER`, which rounds to the ~15.6 ms system tick — a 16 ms timer measured **35 ticks/s**, so a 30 fps video was sampled at irregular ~28 ms intervals and juddered even though all 30 frames/s were being delivered. The pump also throttles the seek-bar write-back to 10 Hz so slider layout doesn't compete with rendering.

**Ctrl+Z undoes a delete by moving the item back out of the Recycle Bin, and the item it moves is a shell item, not a file path.** `DeleteRecycleSink` (an `[GeneratedComClass]` `IFileOperationProgressSink` advised on the operation) records `PostDeleteItem`'s `psiNewlyCreated` — the item *as it exists in the Recycle Bin* — as a `SIGDN_DESKTOPABSOLUTEPARSING` string, and `FileUndoService` keeps those per delete (app-wide stack, cap 32). Undo re-creates that shell item and `MoveItem`s it back, which is what dragging out of the Recycle Bin does, so the `$I` record is cleaned up too; moving the raw `$R…` file path instead would leave an orphaned entry behind. Two things follow: the sink must be advised *once per operation* (not passed per `DeleteItem`), and `Advise` takes the interface directly so the source-generated CCW is built for it. Only delete is on the stack — move/copy/rename still pass `FOF_ALLOWUNDO` to the shell but are not tracked here.

**Keyboard shortcuts live in three handlers and which one fires depends on focus.** `Window.OnKeyDown` is the fallback that works when focus is anywhere in the window; `FileList_KeyDown` is attached to the file/filmstrip `ListBox`es and fires first when a row has focus; `GalleryImage_KeyDown` is attached to `GalleryImageArea` (which is `Focusable` and takes focus on click) so Del/F2/Ctrl+X/C/V still work when the user clicked the big preview instead of a row. Each of the two control-attached handlers sets `e.Handled` only for keys it actually consumes, so unhandled keys still reach `Window.OnKeyDown`. When adding a shortcut, decide deliberately which of the three it belongs in — adding it to only one is the usual cause of "the shortcut works in some places". In gallery mode the arrow keys are overloaded three ways and all three live in both control-attached handlers: plain ← / → move between files *unless* a video is playing large (full screen or maximized), where they seek / frame-step; **Ctrl+← / Ctrl+→ always move between files**, which is the escape hatch for exactly that case; and ↑ / ↓ move the gamma slider.

**Type-ahead is on `TextInput`, not `KeyDown`, and it only keeps working because the reveal path restores focus.** Typing letters in the file list jumps to the first item whose `DisplayName` starts with what was typed (`TabViewModel.TypeAheadSelect` accumulates for 1 s, `FindTypeAheadIndex` decides where to land: a single char — or the same char repeated — advances past the current row and wraps, two or more different chars search from the current row so continuing to type refines instead of jumping away). It is attached as `TextInput` on all five file `ListBox`es because that is where the actual character lands after the keyboard layout and IME, which `KeyDown`'s `Key` enum cannot tell you. The trap: selecting the match scrolls, scrolling recycles the `ListBoxItem` containers, and the recycled container took the keyboard focus with it — measured, focus went from `ControlType.ListItem` to `ControlType.Window`, so **only the first letter ever worked**. `RevealEntryInList` therefore ends by focusing the target row (`FocusListItem`), and both it and `CenterListItem` run from a posted `Background` continuation because the row is not realized yet when the reveal is requested. Note also that `FileList_KeyDown` must exclude Shift from its `Ctrl+C` case — it fires before `Window.OnKeyDown`, so without that, Ctrl+Shift+C ("パスのコピー", advertised on the context menu) silently did a plain copy whenever the list had focus.

**`CenterListItem` moves exactly one axis, and picking two breaks the details view.** `TabViewModel.GoUpAsync` reveals the folder it just came out of with `Center: true` so the user can see where they were. Centering both axes looks right in icon views but scrolls the details view horizontally as well — its columns are wider than the viewport — which pushes the 名前 column off screen and leaves the selected row showing only the tail of its name (seen on a real capture: `System32` rendered as `32`). So the rule is: if the vertical extent overflows, center vertically and leave `Offset.X` alone; only when it does not (the 一覧 view fills columns and grows to the right) center horizontally instead.

**Clipboard results are reported twice: the status bar and a toast.** `ActionToast` in `MainWindow.axaml` is one `Border` styled like the drag preview card (accent chip + message), shown by `ShowActionToast(label, message)` for ~1.8 s with a revision counter so a newer toast is not hidden by the previous one's timer. Cut/copy raise it from the view model through the static `TabViewModel.ToastRequested` (the same static-event pattern as `SelectionRestoreRequested`, since tabs come and go and the subscriber is the one `MainWindow`), while the path/link copies call `ShowActionToast` directly from `CopyPathTextAsync`. All the strings it needs already exist (`Text.Clipboard.*` for the message, `Text.Common.Copy` / `Text.Command.Cut` / `Text.Common.CopyPath` / `Text.Command.CopyFolderPath` for the chip) — adding a new toast should reuse those rather than adding a key to all 17 locale files.

**Right-button drag is a first-class drop mode, and the "was it the right button?" answer comes from Win32, not from the event.** Dragging with the right button and releasing over a folder shows Explorer's own menu — ここにコピー / ここに移動 / ショートカットをここに作成 / キャンセル — with the default operation (same drive = move, other drive = copy) in bold. Three things here are not obvious:

- **The drag source needed no OLE work.** Avalonia 12's `OleDragSource.QueryContinueDrag` drops when *no* mouse button remains pressed (and cancels when two are), so a right-button drag runs through `DragDrop.DoDragDropAsync` unchanged. The source-side change is only "arm the drag on a right press too" (`_dragButton`), plus adding `DragDropEffects.Link` to the allowed effects so Explorer offers "create shortcut" when Kiriha is the source.
- **`DragEventArgs` exposes only `KeyModifiers`**, so the drop side cannot see which button is held. `MouseButtonState.IsRightButtonDown` (`GetAsyncKeyState(VK_RBUTTON)`) is sampled on every `DragOver` and latched into `_rightButtonDragObserved` for the session, because at `Drop` time the button is already up. It is deliberately `GetAsyncKeyState` and not `GetKeyState`: for a drag started by another process the mouse messages never enter this thread's queue, so the queue-synchronised `GetKeyState` reports the button as up — which is exactly the case of dragging out of Explorer into Kiriha.
- **The release that ends a right drag must not also open the context menu.** `_suppressContextMenuAfterDrag` is set when a right drag starts and consumed by `FileList_PointerReleased` / `Sidebar_PointerReleased`; it is also cleared at the top of every `PointerPressed`, because after the OLE loop the matching `PointerReleased` does not always arrive and a stuck flag would swallow the *next* right-click. Marquee selection stays left-button-only, so a right drag on the background just falls through to the background menu.

**Tabs are spring-loaded: hovering one for 1 s during a drag switches to it**, which is the only way to drop onto a folder that lives in *another* tab (`UpdateTabHoverSwitch` / `ResolveHoveredTab`). Two things it has to work around. The dwell target is tracked by `TabViewModel` identity with a revision counter, and hovering the **drop-preview tab** deliberately keeps the previous target instead of clearing it: dropping onto a tab's upper half inserts the preview *above* it, so the row under the pointer becomes the preview and a naive "no tab under pointer → cancel" would make the switch never fire. The strip's own drop semantics are unchanged — releasing anywhere on the tab strip still opens the dragged folder in a new tab.

**`OnDrop` must decide *which region* was dropped on before calling `ClearFileDropVisual`.** That call removes the preview tab, which detaches `e.Source` from the visual tree, so `IsOnVerticalTabStrip` / `IsOnBookmarkBar` — both of which walk visual ancestors — flip from true to false partway through the handler (measured: `strip=True` before the clear, `strip=False` immediately after). The symptom is a drop that silently does nothing: the tab-strip branch is skipped and the file-list branch finds no target. `isOnBookmarkBar` / `isOnTabStrip` / `tabStripDropZone` are therefore captured up front, next to `previewIndex`, which already existed for the same reason.

`ShellLinkService` is the shortcut half (`IShellLink` + `IPersistFile`, source-generated COM). Naming follows Explorer — 元の名前（拡張子込み）+ `Text.Drop.ShortcutSuffix` + `.lnk`, with ` (2)` on collision — and `BuildShortcutFileName` takes the existence check as a delegate so `ShellLinkTests` can pin the rules without touching the disk. Note when testing this by automation: synthesising a right press with `SetCursorPos` immediately after the pointer teleports into the window loses that first press to window activation, so prime the window with an ordinary click first — an intermittent "the menu did not appear" in a script is usually this, not the feature.

**A large amount of interaction logic is necessarily in `Views/MainWindow.axaml.cs` code-behind**, not pure XAML bindings — context menus that are built dynamically (shell menus, "New" submenu from `ShellNewService`, bookmarks bar nesting), drag-and-drop (both from-OS and to-OS), multi-key keyboard shortcuts, and Win32 handle lookups (`TryGetPlatformHandle()`) can't be expressed declaratively. Grep for the specific `_Click`/`_PointerReleased`/`_KeyDown` handler name before assuming logic doesn't exist yet.

**Feature definitions are catalog-backed.** `ContextActionCatalog` (tab scope only) feeds the tab context menu's "タブの詳細操作" group. Adding or renaming an action requires keeping the catalog entry, its dispatcher/handler in `MainWindow.axaml.cs` or `MainWindowViewModel`, and the catalog's startup validation in sync.

**Nothing on the enumeration path may read an Avalonia property, because that path runs on the thread pool.** `MaterialIconService.IsLightTheme()` used to return `Application.Current.ActualThemeVariant == Light`; `FileSystemService.GetEntries` calls it once per enumeration and is itself invoked from `Task.Run` inside `NavigateToAsync`, so Avalonia's `VerifyAccess` threw `InvalidOperationException: The calling thread cannot access this object` and the whole enumeration failed — **every folder the user opened showed "フォルダーを開けませんでした"**, but only with the Material icon set, since `preferLight` short-circuits on `IconSet == Material` and the other two sets never call it. `IsLightTheme` now returns a `volatile bool` filled in by `AttachThemeWatch` (called from `App.OnFrameworkInitializationCompleted`, which also subscribes to `ActualThemeVariantChanged`). Reproduced and verified both ways with `IconSet=Material` on a real run.

**Theme and accent color are not static resources** — `App.axaml` defines Light/Dark/OneDark/Dim `ThemeDictionaries` for the Chrome-ish chrome (tab strip bg, omnibox bg, etc.), and `ThemeService` pushes the live Windows accent color into Avalonia's `SystemAccentColor*` resources on startup and on every `PlatformSettings.ColorValuesChanged`. Don't hardcode colors in new views — use the `DynamicResource` keys already defined in `App.axaml` (`TabStripBg`, `ContentBg`, `TextPrimary`, etc.) so all themes, acrylic switching, and live accent-color changes keep working.

**A control that shows an on/off state borrows the vertical tab's chip tokens** — `ToggleButton.chip` (the sidebar's クイックアクセス / ツリー表示 toggle) paints `TabIdleBg` / `TabHoverBg` / `TabSelectedBg` plus the same 2 px accent edge when checked, because the tab strip is the only place in the app where "state as a filled surface" is already defined. Fluent's default `ToggleButton` theme writes its own background straight onto `/template/ ContentPresenter`, so setting `Background` alone is not enough: the class replaces the whole `Template`, exactly like `ListBox.verticaltabs ListBoxItem` does.

**The selected vertical tab uses `TabSelectedBg`, which is deliberately a different key from `TabActiveBg`.** `TabActiveBg` is the "surface that continues from the active tab" and is shared by the address-bar row, the bookmarks bar and the tab drag ghost, so it stays equal to `NeutralBase`; painting the selected tab with it made the tab invisible against the strip (only its 2 px accent edge showed) once the acrylic scrim started rendering that colour for real — before, the strip was blurred wallpaper, so it only *looked* fine by accident. `TabSelectedBg` (`NeutralElevated`, one step lighter than `TabIdleBg`) gives every theme the same "selected is the brightest chip" relationship Light already had with `#FFFFFF`. Changing `TabActiveBg` to fix a tab-strip problem will visibly lighten the address-bar band — check all four usages before touching it. `TabActiveBg` is also **rewritten at runtime with `ChromeAlpha`** like the other chrome surfaces, because leaving it as the static opaque colour made the address-bar and bookmarks-bar band stay at 100 % while everything around it went translucent — one bright slab across the top, immediately obvious once the alphas are lowered. Its base colour is kept as its own `…TabActiveBg` constant per theme rather than reusing `…TabStripBg`, since Light is `#FFFFFF` there while the tab strip is `#DEE1E6`.

**The content island's outline is a separate sibling `Border`, on purpose.** `ContentIsland` clips its children with a rounded `RectangleGeometry` matching its own bounds (rectangular `ClipToBounds` can't follow a `CornerRadius`). Giving that same element a `BorderThickness` looks fine on the straight edges but the clip shaves the 1 px stroke off the four arcs, so the corners render as a visible gap — the symptom is "the rounded corners' line is broken". The outline therefore lives in an unclipped `Border` drawn after it.

**`ExperimentalAcrylicBorder` must be hidden when acrylic is off** (`IsVisible="{Binding OptUseAcrylicBackground}"`; `ThemedDialogWindow` does the same from code-behind). Left visible with `TransparencyLevelHint = None`, it still paints its fallback material over the whole window — measured on One Dark, the window base rendered `#434447` instead of `#21252B`, i.e. every un-surfaced area was lifted ~13 % toward white and lost its blue cast. That is what made acrylic-off look like a different theme rather than the same theme without blur.

**Acrylic density is controlled by the scrim `Border`, not by the acrylic material.** **No `ExperimentalAcrylicMaterial` in the app sets `MaterialOpacity` or `TintOpacity` — they are deliberately left at Avalonia's defaults (0.5 / 0.8, read back at runtime to confirm), and only `BackgroundSource` and `TintColor` are written.** The five declarations (main window, `ThemedDialogWindow`, `TextInputDialog`, both context-menu popups) had drifted into a 0.85/0.9 camp and a 0.65/0.8 camp; writing any number there implies it matters, and it does not. Measured A/B on the vertical tab strip — the one place where nothing but the scrim covers the acrylic — 0.85/0.9 gives `#1C2730` and the defaults give `#1E2832`, a 1–2/255 difference. So don't reintroduce these attributes: the knobs that actually change how dense the acrylic looks are `ThemeService`'s `ScrimAlpha` / `ChromeAlpha` / `MenuAlpha` / `ContentAlpha`, because `MaterialOpacity`/`TintOpacity` barely move the result on Win32 (also measured: 0.85 → 0.97 changed the sampled pixel by one step), because `BackgroundSource="Digger"` digs through the window down to the DWM blur — which also means making `Window.Background` semi-opaque does nothing. So `MainWindow.axaml` and `ThemedDialogWindow.axaml` each paint a plain `Border` **above** the `ExperimentalAcrylicBorder` whose brush is `AcrylicScrimBrush` (the current theme's tab-strip colour at `ScrimAlpha`, set by `ThemeService`, transparent when acrylic is off). Without it, only the areas with no surface on top — the tab strip and the space behind the vertical tabs — show the raw blurred wallpaper and read as a different colour from every opaque panel. When measuring this, note that `Graphics.CopyFromScreen` does **not** capture DWM-composited blur: it returns the wallpaper for acrylic regions no matter what is drawn, so verify with a real screen capture instead. **A new theme is four edits that must land together**: the `ThemeVariant` field on `ThemeService` (custom variants can only be reached from XAML via `x:Static`, and `InheritVariant: Dark` is what makes Fluent's own resources fall back sanely), its `ThemeDictionary` in `App.axaml`, the acrylic base colors plus the `ApplyAcrylicBackgrounds` / `ApplyClassicMenuTheme` branches, and the `ApplyTheme` case in `MainWindowViewModel` next to the settings `ComboBoxItem`. Miss the acrylic branch and the theme silently renders with the *previous* theme's tint while acrylic is on.

**Auto-update is Velopack**, wired the same way as the sibling project `Lhamiel` (`../Lhamiel` — check there first if extending update behavior, it's the reference implementation this was copied from). `Program.cs` runs `VelopackApp.Build().Run()` before the Avalonia app starts; `UpdateService.Check4Update` uses `SimpleWebSource` against the fixed Cloudflare R2 base URL and opens the download/apply dialog. `VelopackUpdateDialog`/`Velopack` are explicitly root-assemblies in the csproj (`TrimmerRootAssembly`) because their view models are only reached via compiled XAML bindings and would otherwise be trimmed by AOT.

**File-type icons are raster PNGs, not SVGs — this was a deliberate reversal, not the original design.** `Assets/MaterialIcons/` bundles [material-icon-theme](https://github.com/material-extensions/vscode-material-icon-theme) (MIT; see `NOTICE.md` there) as pre-rasterized 256×256 PNGs plus a `manifest.json` (extension/filename/folder-name and light-theme mappings → icon key, derived from the npm package's `dist/material-icons.json`). `MaterialIconService.ResolveIconKey` does the name→key lookup (exact filename → lowercase filename → extension → default), and `GetImage` loads/caches the PNG as an `IImage` through `AssetLoader` + `Bitmap`. **Do not swap this to runtime SVG rendering** (for example `Avalonia.Svg.Skia`): that route was tested and produced a fully black, never-composited window without a managed exception. If material-icon-theme's upstream icon set needs refreshing, the reproducible pipeline is: pull the npm tarball → use `dist/material-icons.json` plus `icons/*.svg` → rasterize with `resvg` → replace the PNGs and manifest in `Assets/MaterialIcons/`. The icon set is selected via `ShellOptions.IconSet` (`FileIconSet.Original` emoji / `Material` / `Windows`), persisted as the enum name string in `AppSettings.IconSet`; the legacy `AppSettings.UseMaterialIcons` bool is migrated on startup in `MainWindowViewModel` and then kept false — don't remove the old field, old settings.json files still carry it. The third set, `Windows`, renders the real Explorer shell icons: `ShellThumbnailService.TryGetIcon` (`SIIGBF_ICONONLY`) loads them lazily per visible row via `TabViewModel.EnsureWindowsIconAsync` (viewport/DataContext events in `MainWindow.axaml.cs`, plus a `SelectedTab`-change trigger so rows realized while the settings tab was frontmost get filled in). The sidebar (quick access, drives, recycle bin, recent files) follows the same setting through `RefreshSidebarAsync`, which precomputes an icon map off-thread; sidebar-owned shell `Bitmap`s are disposed on rebuild, while Material `IImage`s are shared with `MaterialIconService`'s cache and must never be disposed.

## Conventions specific to this repo

- Code comments, XML docs, log messages and commit messages are Japanese (see any existing file). Keep writing them in Japanese to match. User-facing strings are the exception: they are no longer literals at all — add a `Text.*` key to every locale file and reference it (see the localization section).
- No dependency injection container — everything is constructed directly and wired via constructor params / shared instances passed down from `MainWindowViewModel`.
- For app-supplied helper commands (terminal, PowerShell, cmd, Explorer, editor), use `TrustedProcessLauncher` and argument lists instead of concatenating a command line. Direct `UseShellExecute` remains appropriate when opening the user-selected file itself through its registered shell handler.
- Avalonia 12's `WindowDecorations="BorderOnly"` is used deliberately so the custom-drawn caption buttons in the tab strip don't double up with OS-drawn ones — if captions ever look doubled, this is the property to check, not a bug in the custom buttons. `MainWindow.ApplyWindowDecorations` drops it to `None` while maximized or full screen: with `BorderOnly` a maximized window is 7 px larger than the monitor on every side (measured 2062×1118 against a 2048×1152 monitor), which is the classic Win32 maximize overhang. It must be applied **again from `Opened`** — writing `WindowDecorations` before the platform window exists is silently lost, which is exactly what happens when the app restores into a maximized state. Verified by measurement that this does **not** make the window swallow the taskbar: maximized, `GetWindowRect` equals the monitor's *working* area exactly (0,0–2048,1104), and `WS_THICKFRAME` comes back on restore.

**The "frame" users see around a maximized window is mostly not the OS border — it is the content island's own 6 px margin plus its 1 px outline.** `MainWindowViewModel.IsGalleryEdgeToEdge` (gallery full screen, or maximized while in gallery) drives `ContentIslandMargin` / `ContentIslandCornerRadius` / `IsContentIslandOutlineVisible` / `GalleryImageMargin` so the picture reaches the physical screen edge; outside gallery the Chrome-ish rounded island is unchanged. Two traps when touching this: the clip `RectangleGeometry` is **not** in the logical tree, so `$parent[Window]` does not resolve there — it takes its radius from the Border via `ElementName=ContentIsland`, `CornerRadius.TopLeft`; and `IsWindowMaximized` has to be pushed in from `MainWindow` (both from the `WindowState` property change and once after restore), since the view model cannot see the window state.

**Screenshots of this app can be taken headlessly with `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)`** even when the console session is locked, which `Graphics.CopyFromScreen` cannot do. That is the way to verify layout changes here: capture the current build and the installed release the same way and compare pixel extents.

**The app can also be *driven* headlessly through UI Automation**, which is how to verify an interaction end to end (click a real button, then read the clipboard or the status bar) without a human at the keyboard. Avalonia exposes automation peers on Windows, so `System.Windows.Automation` from PowerShell can find the window by process id and invoke controls. Three practical notes: run it from `pwsh` with `-STA` — a `.ps1` containing Japanese literals executed by Windows PowerShell 5.1 is read as ANSI and every `NameProperty` lookup silently misses; controls are found by their `AutomationProperties.Name`, which is exactly why new icon-only buttons should carry one; and a file row's name lives on a child `Text` element, not on the `ListItem`, so select a row by finding the `Text` and walking up with `TreeWalker.ControlViewWalker` until `ControlType.ListItem`, then use `SelectionItemPattern`.
- `ApplicationIcon` (exe icon) and the `AvaloniaResource` `icon\app_icon.png` (window/taskbar icon) are two independent things that both need updating if the icon changes.
